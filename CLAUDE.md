# Nova: Shoe Rental Marketplace

An asset-light marketplace for renting sneakers by wear. Merchants list shoes, borrowers curate wardrobes and hold as many pairs as they want simultaneously (wear is divided 1/n across all held pairs on a falling price curve), discovering shoes through curated lifestyles, moments and occasions rather than a technical shoe catalog. Ride-hailing drivers move the shoes, and the platform runs pricing, booking, payments, payouts and trust. We own no shoes and run no couriers.

- Full brief: [docs/business-model.md](docs/business-model.md). Cite sections as §n.
- Rent calculation spec (authoritative for pricing and wear): [docs/pricing-spec.md](docs/pricing-spec.md). It merges the reference rent engine (Formula Guide v2 / `rental_pricing_engine.py`), whose tests now live in `src/lib/pricing/__tests__/acceptance.test.ts`.

## Stack

Next.js (App Router) + TypeScript · PostgreSQL + Prisma · decimal.js for every money and wear value · Vitest (unit) + Playwright (e2e) · object storage for photos behind an adapter · payment gateway behind an adapter for token top-ups (sales) and withdrawals (refunds); PayHere is a candidate, the mock ships first.

Versions: Next 16.4, React 19.3, Prisma 7.10 (config in `prisma.config.ts`, client generated to `src/generated/prisma`, uses the `@prisma/adapter-pg` driver adapter), Vitest 5, Playwright 1.64. Next 16 differs from older versions, so read @AGENTS.md before writing Next.js code.

Shared decimal helper: `src/lib/decimal.ts` (`D`, `toD`, `roundMoney`). Use it rather than creating new Decimal configs. Convert Prisma Decimals with `toD`, never via `Number()`.

Conventions:

- **Cache Components is off** (`next.config.ts`). Pages that read the session render dynamically. Don't add `"use cache"`.
- **Auth:** call `requireUser(...roles)` from `src/server/auth/session.ts` at the top of every page, server action and route handler that needs a user. It redirects on failure. Sessions are random tokens in an httpOnly cookie, stored as SHA-256 hashes.
- **Server code** lives in `src/server/<module>/`, imports `server-only`, and uses `db` from `src/server/db.ts`. Pages call services; services hold the business logic and are integration-tested.
- **Prisma 7:** `prisma migrate dev` does not regenerate the client, so use `npm run db:migrate` (migrate + generate).
- **Wording and listings (product owner, 2026-10-12):** the website says **"per day"** (prices) and **"days"** (counts, lifespans), never "wear-day"; that term stays in code, the engine and the specs. **Brand and model are optional** (stored as ""; show names with `shoeName()` from `src/lib/shoe-name.ts`, "Unbranded shoes" when both are empty). A pair has **one or more experiences** (`Shoe.experiences`, checkbox chips in `StyleFields`; read forms with `formFields`). The merchant Payouts page has no description line.
- **Your Nova Closet (`/closet`, product owner, 2026-10-13):** a rotation planner. The visitor first picks **who it's for and a size** (`?for=men&size=UK+9`), and only pairs that fit and can be booked are offered (`browseShoes`), so a rotation never mixes sizes. Slots are the moments of the week (adults: Morning Run, Work Day, Weekend Stroll, Night Out; kids: School Day, Sports Day, Playtime, Party Time), named with the same experience names as filters and listings; "+ Add another pair" adds extra slots (removable), since pairs are unlimited. "Choose a pair" on a slot filters the list below to that experience and puts the next pick in that slot; Change, Remove and a search box are there too. The plan starts from the borrower's bundle pairs, then pairs made for each slot (no unrelated fill), and is kept as a draft in the `nova_closet` cookie (`src/lib/closet.ts`) so a reload or sign-in keeps it. Prices come from the server (`shoePricing`) and the total from `bundleDailyCost`; each pair shows its own price per day (never struck through, never divided by n, no "savings" claims) and the bar says "about LKR x per day together". "Add n pairs to my bundle" (`addRotationToBundleAction`, borrowers only) **adds to the bundle, never replaces it**; signed out it is "Sign in to rent these pairs" → `/sign-in?next=/closet`, and sign-in returns to a same-site `next` path. No wear figures, no blue text, no "luxury" or "equip" copy.
- **Back buttons (product owner, 2026-10-13):** every sub-page has a "← Back" button at the top (`BackButton` in `src/components/back-button.tsx`; `NavTracker` in the root layout). Borrower pages reached from many places (a shoe `/shoes/[id]`, a style pack `/packs/[id]`, `/size-guide`) use `useHistory`: Back returns to the previous page of the site (keeping Browse filters), or to the fallback (`/browse`, `/`) when opened directly. Other sub-pages always go to their list: merchant shoe and Add shoe → `/merchant`, record condition → `/merchant/returns`, pack new/edit → `/merchant/packs` or `/admin/packs`, confirm condition and report a problem → `/rentals`, forgot password → `/sign-in`. Top-level nav pages have none. A new sub-page gets one too.
- **Experience culture & lifestyle discovery (product owner, 2026-10-12/13):**
  - **Lifestyle moments over shoe catalog:** The home page leads with **Curate by Moment & Occasion** (`OccasionDiscovery` in `src/components/occasion-discovery.tsx`), featuring authentic lifestyle photography, frosted glass icons and clean titles: *Morning Run & Performance*, *The Daily Commute & Work Day*, *Weekend Stroll & Brunch*, *Night Out & Big Occasions*. No verbose taglines or clutter on the cards.
  - **Curated Rotations & Style Packs:** (product owner, 2026-10-13) merchants and admins make curated rotations (`StylePack` → `StylePackRole` → `StylePackRoleShoe`; service `src/server/packs/`). A pack has a title, an optional subtitle and "Rotation advantage" line, and 1–8 roles; each role (name, optional description and experience) is filled by 1–4 **real listed pairs from any merchant**. A merchant's pack is a DRAFT until they send it for review (SUBMITTED); an **admin approves it before borrowers see it** (PUBLISHED) or rejects it with a reason (REJECTED, the merchant is notified with kind STYLE_PACK, edits and resubmits). A merchant editing a published pack sends it back for review. Admins can publish their own packs straight away, unpublish any pack (optional reason, merchant notified), and edit or delete any pack. Published packs show on the home page (`CuratedPacksShowcase`, newest first) and at `/packs/[id]`, where a borrower can add one bookable pair per role to the bundle ("Add the rotation to my bundle") or single pairs. Pairs that leave the catalogue drop out of a pack. **Packs carry no price or discount of their own**: each pair is rented at its own curve price, and the "about LKR x per day held together" line is `bundleDailyCost` of one pair per role (engine output). Manage at `/merchant/packs` and `/admin/packs` (nav "Style packs"). The seed publishes three examples (*The Marathon & Active Recovery*, *The All-Week Urban Wardrobe*, *The 24/7 City Explorer*).
  - **Unlimited pairs:** Borrowers can hold **any number of shoes** they want at once. There is no 4-pair cap in checkout, bundle storage or UI copy. Daily wear is split 1/n across all pairs held, keeping daily rent balanced.
  - **Browse & discount titles:** Browse page header is titled **"Elevate Your Everyday"** without technical subtitles. The home discount row subtitle is **"Unmatched Value, From Day One"**.
  - **Card minimalism:** Browse cards show strictly essential attributes: photo, model name (or `shoeName()`), one size, rent price per day, and condition badge. All discount badges use uniform sizing (`DiscountBadge`, `80px` × `24px`).
- **Pricing method (product owner, 2026-10-11; pricing-spec.md decision 11, §2):** the merchant picks each listing's curve, **S-curve (logistic decay)**, the default, or **exponential decay** (Q = q^(w/L)). Same floor q, target R and P(L) past L. Stored as `Shoe.pricingMethod`; changeable only while a draft (`updatePricingMethod`), fixed once published. `shoeCurve` passes it to `curveParams(V, L, settings, method)`, so always price through `shoeCurve`.
- **Settings:** a listed shoe is priced with the settings version it was listed under (`Shoe.settingsId`). Use `shoeCurve(shoe)` / `shoePricing(shoe)` from `src/server/catalogue/pricing.ts` (include `settings: true` in the query). `getActiveSettings()` is for operational values (token cover, bundle size, windows, fees), new listings and previews.
- **Brand (product owner, 2026-10-11):** the site is called **Nova** (renamed from Shoe Rental, product owner 2026-10-12), and UI text says "shoes", never "sneakers". The only website colours are pure white (#FFFFFF), pure black (#000000) and one blue, **#35D6ED**: tokens in `src/app/globals.css` (`paper`, `ink`, `accent`, `on-accent`; greys are black or white at low opacity; `good` / `warn` / `danger` / `info` map onto black or white). The blue is a fill (primary buttons, the sign-up button, search button, good badges, the logo mark, the price chart) with black text on it (`text-on-accent`); never blue text on white (contrast too low). Status shows by shape, not colour: good = blue pill, problem = black pill or black-outlined alert, warning = outlined. Don't add another colour. Photos and emoji icons are content, not palette. **Day and night mode:** every colour token is `light-dark(day, night)` in `globals.css`; the page follows the device setting until the visitor uses the header switch (`ThemeToggle`, sun/moon, "Switch to night mode" / "Switch to day mode"), which sets `data-theme` on `<html>` and a `theme` cookie (1 year) that the root layout reads, so the server renders the picked mode with no flash. Night mode is black background, white text, the same blue. New colours go in as `light-dark()` tokens, never as `dark:` classes.
- **Sizes (product owner, 2026-10-11):** a merchant lists a pair in the size on its label, **UK, EU or US** (`Shoe.sizeSystem` + number; `size` is the label, e.g. "EU 39"), and we store the same size in every system, `sizeUk` / `sizeEu` / `sizeUs` / `sizeCm` (cm = foot length), from the product owner's charts in `src/lib/shoe-size.ts` (`shoeSizeFields`): women's pairs use the women's chart, men's and unisex the men's. Kids' pairs and sizes off the chart keep only the listed system (no kids' chart yet). Changing who a pair is for re-reads its label size on the new chart. Borrowers search in any system (`?size=UK 6`, `EU 39`, `US 8.5`, `24.5 cm`) and find a pair however it was listed; a size search shows what that size is in the other systems on each chart (`SizeEquivalence`), cards show the listed size plus the borrower's system (`sizeSummary`, e.g. "EU 39 · UK 6"), the listing shows all four (`ShoeSizePanel`), and `/size-guide` shows both charts with the size highlighted. Never edit the charts without the product owner.
- **Stock per size (product owner, 2026-10-13):** a merchant lists a shoe once with the size system on its labels and **how many pairs they have of each size** (rows of size × pairs, `StockFields`; at most 20 pairs a size and 100 a listing, each size once). Every pair becomes its own `Shoe` row (its own size, wear, price, deposit and rentals, as before), all sharing a `listingId` and the same five photo files (one Photo row per pair). Publishing, deleting a draft, the pricing method and who it's for / experiences apply to the whole listing; retiring, cleaning and renting stay per pair. Borrowers see **one card per listing** (`groupByListing` / `cardPair` / `sizeRange` in `src/lib/listing.ts`): the pair with the biggest discount, then the lowest price, and the sizes on offer ("UK 7, 8, 9"; "From" when prices differ). The listing page has a **Sizes** picker (`listingSizes`): each size with how many pairs are free, or "reserve next"; picking one opens a pair of that size. The merchant's pair page has a "Pairs in this listing" card (`listingStock`). Sample listings declare `stock` in the seed (Dunk Low UK 8, 10 × 2, 11; Ultraboost Light EU 38 × 2, 39, 40; Revolution 7 Kids UK 12, 13 × 2).
- **Forgot password (product owner, 2026-10-11):** "Forgot password?" on sign-in → `/forgot-password` emails a one-time link (`requestPasswordReset`, `src/server/auth/password-reset.ts`) valid 60 minutes, at most one email per account a minute; the page says the same thing whether or not the email has an account. `/reset-password?token=` sets the new password (`resetPassword`): the link and every other open link stop working and all sessions are signed out; then sign-in shows "Your password has been changed". Only the token's SHA-256 is stored (`PasswordReset`). Links use `APP_URL`, never the request's Host header. With the mock mailer outside production, the page shows the link, since no email really goes out.
- **Addresses:** Each customer and merchant account has **exactly one address** and its **city** (separate fields, both required at sign-up) with the reason shown next to the field (customers: where pairs are delivered and collected; merchants: where pairs are picked up and returned). It can be changed later on the account page (`/account`, `/merchant/account`); trips copy the addresses when they are booked, so a change applies to trips booked after it. There is no address at checkout or per listing (product owner, 2026-10-11). Trips use "address, city" (`fullAddress` in `src/lib/address.ts`) through `customerAddress` / `merchantAddress` (`src/server/booking/addresses.ts`); a customer without one can't book and a merchant without one can't list.
- **Trips:** delivery fees are not handled by us. Whoever receives the pair pays the driver directly in the ride-hailing app: the borrower for deliveries, the next borrower for handoffs, the merchant for returns (`Delivery.paidBy`, set by `receiverPays`). Never charge, collect or refund a trip fee in tokens, and there is no booking fee.
- **Days:** wear-ledger days are Asia/Colombo calendar dates in `RentalItem.firstDay` / `lastDay`, both counted. Day 1 is the day after delivery (the delivery day is free); the last day is the day the borrower presses End rental, or the term's last day (`termEndDay`), so waiting for the driver is free. A handoff receiver starts the day after delivery, or the day after the giver's last day if that is later.
- **Fixed terms, post-paid rent (pricing-spec.md §6, §6a, §7):** a borrower books a term; nothing is charged at booking. Each pair's value is locked as its own deposit (purpose `DEPOSIT`) and its rent estimate beside it (`RENT`, `rentLocked`), both until that pair's item closes; `closeItem` then calls `collectRent` (release the rent lock, charge the actual rent) in the same transaction, so a merchant share is payable only once the rent is collected. Only available tokens can be withdrawn. An early return needs `earlyReturnNoticeDays` (10) notice (`scheduleEarlyReturn`); only the free-return window or the term's last day ends at once. A pair can be booked for any term while `committedWear` < L, never after; past L each wear-day is charged at the end-of-life price P(L) until it is returned (`chargePastLife`). Each pair's `committedWear` (what listings show, and what the next borrower is priced at) includes every open booking's planned wear. Anything that changes a plan (delivery, early-return notice, extension, a new overlapping booking, cancellation, lost pair, close) calls `replan` (`src/server/booking/plan.ts`), which moves each rent lock to the new estimate, or makes an offer (new first day and price) to a reserved-next borrower whose start moves earlier or whose estimate goes up. A held pair can be reserved from its holder's day 1; a declined or expired offer cancels the reservation, unlocks everything and emails the borrower, and the pair stays with its holder, free, until a new borrower books it (`holdForNext`; never collected meanwhile). The daily job (`runDailyRentals`, `/api/cron/rentals`) ends terms that ran out and expires offers. Notices go through `notify` (in-app, plus email via the mock mailer).

## Hard rules (§9)

1. **Prices and wear come only from the pricing engine (`src/lib/pricing/`) and the wear ledger (`src/lib/wear-ledger/`).** No other module computes a price, a charge, a share or a wear value. Adding up engine outputs (a shoe's collected total, payment and payout sums) is bookkeeping and is fine; deriving a new price, share or wear figure is not. Charged amounts come from `chargedAmounts()`: charge rounded, then **merchant first**: the merchant's share fills what they are still owed of (1 + μm) × V, and the platform gets the rest.
2. **Keep values unrounded; round only what is shown or charged, to 2 decimals.** No JS `number` for money or wear. Use decimal.js in code and `Decimal` in Prisma.
3. **Discounts never stack.** Always start from the curve price at the shoe's current wear.
4. **Exact curve ratios:** m = 200·L/365, β = 0.03·365/L, q = 0.30 (S-curve); λ = ln(1/q)/L for exponential decay.

## Agents

Seven subagents live in `.claude/agents/`, each owning specific directories: `pricing-engine`, `backend-data`, `booking-wear`, `logistics`, `payments-payouts`, `frontend`, `qa-review`. An agent edits only its own directories. Cross-module changes go through the owning agent or an agreed interface.

**Git workflow (product owner, 2026-10-11): update `main` after every commit, locally and on GitHub.** Work on a short-lived branch (or on `main`), run `npm run check` and `npm run test:int` (and `npm run e2e` when port 3100 is free) before committing, then merge the commit into local `main` (`--no-ff` for a branch) and `git push origin main` straight away. Local `main` and `origin/main` must never be left behind the latest commit. `qa-review` reviews `main` when asked; it no longer gates merges.
